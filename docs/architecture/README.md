# Архитектура Business Metrics Analyzer

ПЗ № 4. Ровинский Роман Олегович, Корякин Никита Иванович. Группа Б1123-38.03.05ба(1).

## 1. Обзор системы
Веб-приложение торговой компании принимает реестр сделок и рассчитывает выручку, средний чек, конверсию закрытых сделок и рентабельность продаж. Директор и аналитик видят все отделы, менеджер только свой, администратор управляет доступом и целями без доступа к продажам по умолчанию.

Это проект целевой архитектуры, а не утверждение о готовности веб-приложения. Существующий консольный `main.py` сохраняется. Основа: [требования](../business_requirements.md), [истории](../user_stories.md), [Use Case](../use_case_diagram.puml), [backlog](../product_backlog.md).

### Согласование исходных данных
Требования предыдущей работы задают двух участников, CSV до 100 000 сделок, атомарную замену полного набора, XLSX во втором спринте и уведомления внутри приложения в третьем. Методичка ПЗ № 4 задаёт верхнюю проектную ёмкость до 1 млн записей, JWT, Docker, Excel/API, PDF и SMTP. Сохраняем прежние критерии приёмки. Проектируем путь к 1 млн записей и порты будущих интеграций, не включаем их автоматически в MVP. Сроки и показатели производительности пока являются целями, не результатами измерений.

## 3. Выбранный архитектурный стиль
Слоистый модульный монолит с элементами Clean Architecture. Один репозиторий, одна версия образа приложения, API и worker запускают ту же кодовую базу разными командами. Auth, Import, KPI, Reports, Users и Audit являются модулями, а не независимо развиваемыми микросервисами.

Presentation вызывает Application. Application зависит от Domain и портов. Infrastructure реализует порты, composition root связывает реализации. Domain не импортирует FastAPI, SQLAlchemy или Redis. Микросервисы добавили бы распределённые транзакции и сложность эксплуатации для двух участников. Монолит без слоёв затруднил бы проверку формул. Цена выбранного решения: общая БД, совместный релиз и необходимость соблюдать границы модулей.

### Импорт и согласованность
POST /imports проверяет роль аналитика, лимит размера, сохраняет входной CSV в приватное объектное хранилище и создаёт job в PostgreSQL. Возвращает 202 и job_id. Worker выбирает job с lease и `FOR UPDATE SKIP LOCKED`, валидирует поток, пишет пакеты в невидимую staging-версию. Ошибки с номером строки сохраняет в отчёт, активную версию не меняет. Хеш SHA-256 файла уникален для успешных загрузок. Неудачный job можно повторить, незавершённый staging очищается по сроку хранения.

После полной проверки worker берёт блокировку строки активного набора и одной транзакцией публикует dataset_version, аудит успеха и outbox-событие. Параллельные публикации сериализуются, проверка ожидаемой предыдущей версии предотвращает тихую перезапись. Читатель фиксирует version_id в начале запроса. Поэтому частичный набор никогда не виден. Аудит ошибки записывается отдельной транзакцией после rollback.

Outbox обрабатывается повторяемо: уникальные ключи потребителя предотвращают дубли уведомлений `(department, month, version)`. Redis хранит только производные агрегаты. Ключ включает версию данных, разрешённые отделы и период. Смена прав заново вычисляет scope до чтения кэша. Отказ Redis ведёт к SQL, а не к отказу бизнес-операции. Отчёт фиксирует version_id, период и scope, а скачивание повторно проверяет текущие права.

### Данные и KPI
Sale соответствует схеме CSV из требований. PostgreSQL хранит суммы NUMERIC, Python использует Decimal. Агрегаты: сумма amount/cost для won, число won и lost. Средний чек R/won, конверсия won/(won+lost)*100, рентабельность (R-cost)/R*100. При нулевом знаменателе API отдаёт null, UI показывает «Нет данных». Open исключены. Итог по отделам считается из сумм, не средним процентов. Период включителен. Произвольные формулы запрещены, администратор меняет только месячные цели.

## 7. Технологический стек
Целевой стек: Python 3.10+, FastAPI/Uvicorn, SQLAlchemy, PostgreSQL 16, Redis, Docker, Nginx, pandas для ограниченных выборок, openpyxl для XLSX, ReportLab для будущего PDF, S3-совместимое хранилище. Большой CSV читается потоково, целиком в pandas не загружается. Версии библиотек и образы закрепляются при реализации с проверкой совместимости. Это не изменение зависимостей консольного прототипа.

## 8. Ограничения и компромиссы
Топология одного облачного узла не обеспечивает высокой доступности. Redis необязателен для корректности. Worker изолирует тяжёлую обработку, но конкурирует за ресурсы. Начальные ресурсы и меры восстановления: [deployment.md](deployment.md). На 1 млн записей нужен отдельный нагрузочный прогон и, возможно, более мощный узел. Показатель ≤3 с не считается доказанным диаграммой.

JWT сам по себе не обеспечивает немедленный отзыв. Каждый запрос проверяет в БД active и auth_version, смена прав/блокировка увеличивает версию. Токены и пароли не записываются в логи. Refresh-токен хранится как хеш на сервере и передаётся через Secure HttpOnly SameSite cookie, access-токен хранится только в памяти UI.

## 9. План развития архитектуры
Спринт 1: вход, CSV, четыре KPI. Спринт 2: отчёты/XLSX и UI управления пользователями. Спринт 3: цели, уведомления внутри приложения, сравнение периодов. После согласования: Excel/API/1С, SMTP, PDF и 1 млн записей. Выделение отчётов в отдельный сервис рассматривается при подтверждённом конфликте ресурсов, отдельном цикле релиза или появлении отдельной команды, а не по факту роста числа классов.
