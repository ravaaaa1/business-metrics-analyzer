# Ответы на контрольные вопросы

## 1. Чем отличаются виды требований?

Бизнес-требование описывает цель организации: сократить время получения KPI. Функциональное описывает действие системы: загрузить CSV или сформировать отчёт. Нефункциональное определяет качество и условия: обновить дашборд за 3 секунды в 95% запросов на согласованной нагрузке. Ограничение сужает возможные решения: два участника, данные только в рублях.

## 2. Какой должна быть качественная User Story?

INVEST: Independent — самостоятельная ценность с явными зависимостями; Negotiable — детали можно обсудить; Valuable — понятна польза; Estimable — достаточно данных для оценки; Small — объём помещается в спринт; Testable — существуют проверяемые критерии. Формат: «Как роль, я хочу действие, чтобы ценность».

## 3. Для чего критерии приёмки и как они связаны с тестами?

Они задают наблюдаемые условия принятия истории и устраняют разное понимание готовности. Given описывает исходное состояние, When действие, Then результат. Из каждого критерия можно получить приёмочный тест. Дополнительно нужны негативные, нагрузочные и другие тесты для общих требований.

## 4. Какие элементы содержит Use Case-диаграмма?

Акторы вне границы системы, варианты использования внутри неё и ассоциации участия. При необходимости include показывает обязательное включение поведения, extend — условное расширение, обобщение — наследование роли или сценария. Диаграмма не задаёт порядок шагов, он раскрывается в текстовом сценарии.

## 5. Что такое backlog и как его приоритизируют?

Product Backlog — упорядоченный и уточняемый список потребностей продукта. Здесь MoSCoW разделяет Must, Should, Could и Won't в текущем релизе. Приоритет зависит от ценности, рисков и зависимостей. Story Points оценивают относительный объём и сложность, а не приоритет или длительность в часах.

## 6. Как связаны User Stories, Use Cases и backlog?

Story выражает потребность и ценность для роли, Use Case раскрывает взаимодействие с системой, backlog задаёт порядок реализации и плановый объём. В нашей работе связи закреплены ID: BR-04 → FR-05 → US-04 → UC-04 → строка backlog → AC-04.1 и AC-04.2. Соответствие один к одному удобно для этой работы, но не обязательно в любом проекте.

## 7. Какие есть методы сбора требований и когда они полезны?

Интервью раскрывает цели и ограничения заказчика. Наблюдение показывает реальные действия и обходные операции. Анализ документов выявляет существующие отчёты, поля и правила. Опрос помогает собрать мнения большого числа пользователей. Совместный семинар согласует противоречия разных ролей. Прототип позволяет проверить понимание интерфейса. Анализ данных обнаруживает проблемы качества. В этом практикуме используется учебная имитация интервью и анализ предложенного кейса.
